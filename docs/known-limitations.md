# 已知限制与边界

Jync 的 README 只讲它能做什么。这份文档讲清楚它在哪些输入、哪些拓扑、哪些数据形态下**不会替你做决定**，以及遇到时应该怎么办。内容按"会影响选型"的顺序排列。

---

## 1. 什么时候不该用 Jync

| 场景 | 原因 | 更合适的方案 |
|---|---|---|
| 双向同步 / 双活写入 | Jync 是单向管道。两个方向互相回放会形成环，且冲突没有仲裁规则 | 业务层分片写入，或专门的冲突消解中间件 |
| 要求 exactly-once 语义 | 故障恢复采用 at-least-once，重复由幂等 upsert 吸收 | 带事务日志与去重键的流式平台 |
| 单链路持续数十万行/秒 | 单体进程、单节点的吞吐有上限 | Flink / Kafka 集群横向扩展 |
| 同步源库 DDL 变更 | CDC 只回放行级变更，DDL 被跳过并记 WARN（见 4.3 节） | 结构变更走独立的发布流程，或在变更后重建基线 |
| 跨公网、不可信网络直连 | 连接信息与数据在 Jync 进程内解密，部署面按内网设计 | 专线 / VPN / 网关，并启用外部认证与 HTTPS |

## 2. 全量加载

### 2.1 并行有前提

- 并行要求表有**可切分的键**。单列整数主键按 `[MIN, MAX]` 算术切；其他键形态按源库键序采样边界。
- 采样失败（键不可排序、源库不允许该查询、区间退化）时**自动退回顺序分块**，不会失败，但吞吐也回到单线程水平。
- 并行度受连接池反向限制：源与目标为不同连接配置时约为 `max-pool-size - 1`，共用同一配置时更紧。调大并行度前先确认池足够。

### 2.2 无主键表

- 目标为空且存在可排序列时，按 OFFSET 分页，并**以目标当前行数续传**。如果目标表在同步期间被外部写入，续传起点会偏移，可能漏行或重复——同步期间不要手工改目标表。
- 不满足上述条件时，无主键表按单次流式读取完成全量；中断后只能整表重来。
- 全量完成后的行数校验是**单向**的：只确认"源库读过的行在目标存在"，不把目标多出的行判为错误（那可能是业务写入或历史数据）。

### 2.3 同步期间源库的写入

- 全量按块推进，块与块之间源库的新写入由后续增量补齐；但如果某行的主键在块读取过程中被修改，该行可能落在两个块的边界之外。
- 对持续高频写入的大表，最稳妥的做法是：先完成全量，再启动增量；或者直接使用日志 CDC 的"位点 → 基线 → 回放"流程。
- `chunk-size` 同时是崩溃后最多重读的行数。它不是越大越好：块越大，重读成本越高；块越小，提交与检查点越频繁。

### 2.4 延迟索引与外键

- `defer-secondary-indexes` 只延迟**非唯一二级索引**。主键与唯一索引始终立即创建：upsert 依赖主键，唯一索引要尽早暴露源库的重复行。
- 写入期间关闭目标外键是任务级选项。它减少逐行约束检查，也意味着**约束违例不会在中途报错**；全量结束后应由业务或数据库自身复核。

## 3. 增量轮询

### 3.1 轮询看不到 DELETE

- 时间戳、行级 SCN、自增列三种游标都只能看到"出现了哪些新行/被更新的行"。源库的 `DELETE` 不会出现在结果集里。
- 有主键的小表可用 `FULL_COMPARE`：每轮重读整表、按主键 upsert。代价是整表读取；自动选择只在行数不超过 `full-compare-max-rows`（默认 20000）时启用，手动在任务级选择则不受该上限约束；详情页与启动日志会提示超限、或按当前轮询间隔负担过重的表，并给出建议间隔（按约 1,000 行/秒估算，实际以数据库性能为准）。源库删除只在开启「同步行删除」且表行数不超过上限时才会同步（分块比对见下一条）；无主键表只做一次种子加载，之后跳过。
- 超过该上限的表要同步删除，有两条路：日志 CDC，或者把 `sync.delete-compare-max-rows`（默认 0 = 关闭）调大。后者是**分块比对**：把目标表按主键键序翻页，每页只把这一页的主键拿回源库按等值查在不在，内存占用从"整表所有键"降到"一页"。代价是每个周期多扫一遍目标全表、并多出「行数 / 每页键数」次源库查询，所以默认关闭、由运维按表的大小和轮询间隔自行开启；开启后页面与启动日志不再提示该表被跳过。主键上有列清洗规则的表不能走分块（目标库里存的是清洗后的键，回源查不到原始键），仍按上一条跳过。

### 3.2 游标列必须随更新变化

- 时间戳游标依赖源库在每次更新时刷新该列。使用 `ON UPDATE CURRENT_TIMESTAMP`、触发器或应用层赋值都行；**不刷新就永远读不到这次更新**。
- 选列时优先选**系统维护的更新时间**（库自动刷新的 `updated_at`、审计触发器、CDC 自带的变更时间），不要选**业务时间**（下单时间、预约时间、业务日期）。业务时间记录的是"业务什么时候发生"，既可能早于写入，也可能被人工改小；只要它落进已同步的水位线以下，这一行就再也不会被增量窗口读到。系统更新时间保证"写入即刷新、只增不减"。
- 行级 SCN 能捕获 UPDATE，但要求 Oracle 表启用行级依赖（`ROWDEPENDENCIES`）才有稳定的行 SCN。
- 自增列只捕获 INSERT，不捕获 UPDATE。

### 3.3 时钟与水位线

- 时间戳游标以源库时钟为准。源库时钟回拨、事务延迟提交、或应用写入历史时间，都可能让行落在水位线之外。
- 应用服务器与源库的时钟不一定一致。尽量让数据库自己填时间（`NOW()` / `SYSDATE` / 默认值）；只能由应用赋值时，`safety-lag-ms` 应设成不小于两边最大时钟偏差，否则一批行会长期停在水印线以上。
- `safety-lag-ms`（默认 1000ms）把水位线往回拉，让晚提交的事务在下一轮被重新读到；重叠部分由幂等 upsert 吸收。
- 如果业务写入的时间戳可能落后超过 `safety-lag-ms`，请调大该值，或改用行级 SCN / CDC。

### 3.4 行数审计与缺口修复

- 每隔 `sync.row-count-audit-interval-ms`（默认 60 秒，`0` 关闭），每个增量表都会在两侧各算一次"游标列 ≤ 当前水位线"的行数。目标少了，说明有行被水位线挡在增量窗口之外——上面几条描述的情形都会造成这种缺口。
- 缺口不大（不超过 `sync.row-count-repair-max-rows`，默认 1000）且有主键时，审计会**按主键定位出缺的那几行并单独补齐**：只转移主键做比对、只回源取缺失的行，游标保持不动，不触发整表重载。
- 缺口超过上限、表没有主键、或游标列无法在目标侧比较时，退回旧做法——清空游标，下一轮整表重载。
- 反向不修，但要报：目标比源库**多**时，审计不会改动任何数据（多出来的行通常是源库删掉、轮询看不见的删除），只在变更记录里记一条 INFO，并作为数据漂移告警；同一段"多出来"只记一次，等目标行数回落后再次出现才会重新记录。若该表本次周期本来就会跑同步行删除（开启了「同步行删除」且未超过比对上限），则不发这条记录——那些行马上就会被删掉。
- 审计每次都要做全量索引扫描，大表上调小间隔会明显增加源库与目标库的 IO；按表的体量和轮询周期权衡。

### 3.5 至少一次，而非恰好一次

- 游标在目标库提交之后才推进。崩溃会从上一次成功位置重放，因此同一条变更可能被应用两次。
- 幂等 upsert 让重复写入结果一致；但如果目标库上有**触发器、审计表或下游订阅**，它们会看到重复事件。

### 3.6 分析型 / 搜索型引擎作为同步源

Doris、ClickHouse、Hive、Impala、Elasticsearch、MongoDB（Atlas SQL）六种引擎可以参与实时同步，但只有一种角色和两种策略：

- **只做源，不做目标。** 目标端需要建表、按主键 upsert、按主键删改，这六种引擎或没有事务、或没有行级更新，用通用 ANSI 方言写过去属于"能保存、一跑就错"。它们不会出现在项目表单与批量建任务页的目标下拉中，批量建任务接口也会直接拒绝；项目表单的保存接口不做这道硬校验（表单本身不提供这些选项），不要绕过表单直接提交。
- **只有轮询与全表比对。** 没有日志 CDC，因此既不显示任何 CDC 卡片，也不能保存 CDC 策略。需要收敛的场面用全表比对（它会比对并修补差异），轮询只做增量追加。
- **一律按无主键读取。** 这些驱动报告的"主键"其实是排序键或索引信息，不是唯一约束。信它会让增量计划按一个表无法兑现的键推进，目标端的 upsert 还会把源里不同的行折叠成一行——静默丢数据。因此它们的表按无主键处理：**轮询看不到 UPDATE / DELETE，只追加新行**。
- **分页能力分两档。** ClickHouse 与 Doris 支持 `LIMIT n OFFSET m`，无主键大表可按偏移分块并行读取；Hive、Impala、Elasticsearch 与 MongoDB 只有 `LIMIT`，无主键表只能单次流式读取（内存与耗时随表增长）。这是沿用 "无法验证就不启用 OFFSET" 的既有策略。
- **Elasticsearch 的取数上限。** 受 `index.max_result_window`（默认 1 万）约束，超大索引要么调服务端参数，要么只同步窗口内的数据。
- **真实验证覆盖不完整。** v1.12.0 起 ClickHouse 24.8（仅源）在自动化容器里验证了元数据读取、无主键 OFFSET 分块全量、目标建表与空转；MariaDB 11.4 作为源/目标的轮询也进入容器套件。Doris（仅源）与 Elasticsearch SQL（仅源，需自备 X-Pack SQL JDBC）是环境门控测试，本次未运行；Hive、Impala 与 MongoDB Atlas SQL 在本地无法验证，只有单元测试覆盖的 SQL 形状。逐产品的版本、驱动、验证级别与命令见[真实数据库验证矩阵](verification-matrix.md)。上线前仍请对目标版本做一次连通与全量试跑。

### 3.7 内容级校验

v1.12.0 起，增量表在同步成功后会**按主键抽样比对源与目标的行值**，用来发现"行数相同但内容不同"（更新丢失、截断、字符集或类型转换错误）。它只报告，不修复。

- **抽样，不是全表。** 用窗口函数按主键把游标范围内的行分成 N 个桶，每桶取一个键，再按这些键分别读源与目标。默认每表 50 行（`sync.content-audit-sample-size`，范围 2–200）。源端不支持窗口函数或键不可排序时返回 `SKIPPED`，不会退化成 `ORDER BY … LIMIT`（那会总取同一头几行）。
- **默认节流。** 间隔 `sync.content-audit-interval-ms`（默认 15 分钟，`0` 关闭），每个同步周期最多 1 张表（`sync.content-audit-max-tables-per-cycle`），单次查询超时 `sync.content-audit-timeout-seconds`（默认 60 秒）；源行数估计超过 `sync.content-audit-max-rows`（默认 200 万）时整表跳过。
- **不是所有表都能比。** 要求：同步数据、增量策略且游标不是伪列、首次全量已完成、表有主键、主键列没有列清洗规则（否则目标里存的是清洗后的键，回源定位不到）、目标表存在且不缺列、游标列有索引或表未超过 `max-unindexed-scan-rows`。无主键表、`FULL_COMPARE`、ETL 与专属迁移不走这项校验。
- **不可比列排除。** LOB、JSON、XML、几何等没有稳定等值比较语义的列会被排除，并在结果里计入 `skippedColumns`；主键、游标与清洗涉及的列仍按原值比较。数字、时间戳、日期、`OffsetDateTime`、`byte[]` 与 Boolean 会先规范化，字符串按原值比较。
- **只报告。** 发现差异时写一条 INFO 变更记录（前缀 `Content audit: table …`）并发 `DATA_DRIFT` 告警；同一项目同一张表的相同指纹（差异行数 + 目标缺失行数 + 差异列集合）只记一次，避免恒等游标表反复刷屏。目标端的外部触发器、手工转换或历史数据都会表现为差异，因此**不会自动覆盖目标**。
- **成本。** 每次校验在源与目标各做一次索引扫描（取样本键）加一次按键批量读取；大表或索引缺失时可能明显增加 IO。手工"检查内容"按钮绕过间隔，但仍遵守上述资格与行数上限。
- **已知盲区。** 恒等游标（自增列作为游标）看不到已有行的更新，抽样只能发现"被同步过的行值不对"，不能发现"从未进入增量窗口的更新"——后者仍需行数审计、全表比对或日志 CDC。

## 4. 日志 CDC

### 4.1 源库前提是硬门槛

五种引擎都需要在源库开启相应能力并授予额外权限，详见 README 的 CDC 前提表。几个容易忽略的点：

- **MySQL 系**：`binlog_row_image=FULL` 才能拿到完整行；`REPLICATION SLAVE`（8.0.22+ 名 `REPLICATION REPLICA`）与 `REPLICATION CLIENT` 两个权限都要有——MariaDB 10.5 起 `REPLICATION CLIENT` 在 `SHOW GRANTS` 里显示为 `BINLOG MONITOR`，探测两种名字都认；binlog 保留时间必须覆盖最长停机窗口。v1.9.0 起 binlog CDC 不再按产品名拒绝，MariaDB / TiDB / OceanBase 等 MySQL 协议产品都可以选，**能否真正使用由连接时的能力探测决定**：对非原厂 MySQL 的源，探测会真的开一条一次性复制流（server_id 取 4294967294，不占用也不踢掉任何任务），从**上一份** binlog 文件开头读事件，解出一条行事件（TableMap / WriteRows / UpdateRows / DeleteRows）才判通过；解不出就把解码器的原始报错写进检查项。之所以读上一份文件：刚轮转出的当前文件只有 FormatDescription / GTID / CHECKPOINT 事件，没有任何行事件（实测 MariaDB 11.8）。原厂 MySQL 跳过这条流探测——生产里每条 CDC 任务都在持续验证它的线格式。
- **Oracle**：`ARCHIVELOG`、库级补充日志、表级 `(ALL) COLUMNS` 缺一不可；归档保留同样要覆盖停机窗口。
- **崖山（YashanDB）**：没有 LogMiner（23.4.7.100 实测无 `DBMS_LOGMNR` 包与 `V$LOGMNR_CONTENTS`，见 [dm-logminer-spike.md](dm-logminer-spike.md) 第 7 节），也没有 `ORA_ROWSCN`，所以「行级 SCN」游标对它不开放。v1.9.0 起它有了自己的日志 CDC——**YStream 实时日志**（`YSTREAM_CDC`）：用崖山自带的 YStream 引擎，不建触发器、不改表。四个硬门槛：① 源库必须 `ARCHIVELOG` 且连的是主库；② 连接用户需 `CREATE SESSION`、`SELECT ANY TABLE`、`YSTREAM_CAPTURE`、`SELECT ANY DICTIONARY`（缺后两者连 `V$YSTREAM_SERVER` 都看不见）；③ **每张被捕获的表**都要执行一次 `ALTER TABLE ... ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS`——缺了 DML 会静默不进流，所以启动前会再查一遍，缺一张即报错并给出可复制的 ALTER 语句；④ 必须**显式选表**，崖山没有整库自动发现，建服务之后新建的表不会自动进入捕获范围。此外：每个崖山实例最多 32 个 YStream 服务，一个任务占一个，达上限要先删别的任务；服务和 PG 复制槽一样**活在源库上**，删除任务/切走策略/换源连接时会尽力 `STOP`+`DROP`，源不可达则只记 WARN，需人工清理；**停用**的任务不释放服务，仍会让源端继续保留日志。LOB 分块行不支持，遇到即整事务报错、绝不写半行。若不满足以上前提，仍可退回时间戳/数值键轮询或全表比对。
- **PostgreSQL 系**：PostgreSQL 11+（推进位点依赖 `pg_replication_slot_advance`，9.4–10 的探测会失败）；`wal_level=logical`；Jync 会用 `test_decoding` 创建逻辑复制槽，因此该插件必须可用；表的 `REPLICA IDENTITY` 不能是 `NOTHING`。v1.9.0 起 PG 家族（openGauss、翰高、Vastbase、Kingbase 等）也能选 PG 逻辑 CDC，但**能否真正使用由连接时的能力探测决定**：openGauss 5.0 已实测通过（另建议 `enable_slot_log=on`，否则服务器重启后槽不保留，需要重建基线），其余内核需在目标环境自检。探测不是「按品牌猜」：它会建一个一次性逻辑槽，在上面**真跑**消费端要用的 peek 与位点推进语句，再逐表检查 `REPLICA IDENTITY`，任何一条语句不被该内核接受即判不可用，并把服务器原始报错写进检查项 —— 所以「自检」不需要人工拼 SQL，点一次探测即可。
- **SQL Server**：库级 CDC 已启用，且 **SQL Server Agent 必须持续运行**；Agent 停止后 CDC 捕获表不再增长，Jync 看起来"没有变更"。

### 4.2 主键是必需项

CDC 回放依赖主键定位目标行。没有主键的表无法安全地应用 UPDATE / DELETE，应改用轮询或全表比对。

### 4.3 DDL 不会同步

- CDC 流里的 DDL 会被**跳过并记录 WARN**（MySQL、Oracle、YStream 明确如此；PostgreSQL 的逻辑解码流本身不携带 DDL；SQL Server CDC 只捕获行变更）。
- 源表加列、改类型、删列之后，目标表不会自动跟进。绑定缓存会在遇到 DDL 时失效并自愈，但**结构本身需要你另行变更**。
- 结构变更后如果新列必须立即同步，最稳妥的做法是：改完两端结构，停止并重建 CDC 基线。
- **MySQL binlog：DDL 漂移会被发现并停车，而不是写错列**。binlog 行镜像按位置编码，值属于哪一列只由事件期的列序决定。Jync 在每份位点里记下本事务解码所用的列序指纹（列名的 SHA-256，大小写不敏感）：重启时若当前结构已对不上（消费者停机期间跑过 DDL），或流里某份 TABLE_MAP 的列数 / 列名（源库开启 `binlog_row_metadata=FULL` 时）与当前结构不符，任务会停在错误上并提示**重建基线**，而不是把值写进相邻的列。只改类型、不改列名的 DDL 不会触发（位置没有变化）。
- 上述检查有一个已知盲区：源库使用默认的 `binlog_row_metadata=MINIMAL`（不携带列名）时，**列数不变**的重命名 / 换序 DDL 无法被识别；此外，从未被任何已提交事务触及过的表也没有可比较的指纹。若会在停机窗口内做这类 DDL，请改完结构后直接重建基线，或让源库开启 `binlog_row_metadata=FULL`。

### 4.4 大字段可能缺失

- **Oracle LogMiner**：行外（out-of-line）LOB 在 `SQL_REDO` 中没有取值。`sync.cdc.logminer.missing-lob-policy` 默认 `skip`：跳过该变更、计数并在状态面板与限流告警中可见；设为 `fail` 会在第一条此类变更处停住且不推进位点。
- **PostgreSQL**：`test_decoding` 无法还原**未被修改的 TOAST 大字段**。这类 UPDATE 会整行跳过（绝不写入占位值），按表计数并限流告警。要覆盖这类表，请使用轮询 / 全表比对，或接受该列的滞后。
- 其他引擎的大字段行为受源库日志配置（如 `binlog_row_image`）与目标库绑定上限影响，部署前应做一次真实数据验证。

### 4.5 位点、保留期与重建

- 位点记录在元数据库里。**元数据库丢失 = 位点丢失 = 必须重建基线**。
- 源库日志被清理（binlog purge、归档删除、WAL 回收）后，位点无法续读，任务会停在错误上。CDC 的前提检查会给出明确原因，但恢复手段只有重建基线。
- **PostgreSQL 逻辑复制槽被删掉**与日志被清同等严重，而且更隐蔽：人工清理、`enable_slot_log=off` 的 openGauss 重启、备库还原都会让它消失。重新建出来的槽从"现在"开始，已提交位点到现在的变更永远读不到。Jync 在"已提交位点存在、槽却不见了"时判定为 PURGED 并停在错误上（错误文案里带槽名与位点），**不会**静默建新槽继续跑；处理方式同样是重建基线。
- PG 逻辑 CDC 的状态面板会显示复制槽滞留的 WAL 量（`pg_current_wal_lsn() - restart_lsn`，每 30 秒采样一次）。超过 `sync.cdc.pg.wal-retention-warn-bytes`（默认 4 GiB）标红告警，越线的那一刻同时写一条 WARN 日志：槽不再前进时（目标库停机、任务停在错误上、目标写入极慢），这些 WAL 会一直堆在源库上，占满磁盘的后果是整个源库不可用，而不只是这个任务。openGauss 没有 `pg_lsn`，量不出来，这一行不显示（也不去发注定失败的查询）。
- **停用的 PG 逻辑 CDC 任务仍然占着槽**：停机不会 drop 槽（否则重新启用必须重建基线），但采样由消费者执行，任务停着的时候面板上什么都看不到。要长期停用一个 PG 逻辑 CDC 任务，请先确认源库磁盘安全，或直接把策略切成轮询 —— 切换策略、换源库、删除任务这三条路径都会尽力 drop 掉槽（源库不可达时只记 WARN，需要人工清理）。
- 运行中的任务重建基线会立即重新全量装载；已停用的任务只清空进度和错误状态，不会启动消费者，启用任务后才重新全量。全量期间的源库变更由"先记位点、再基线、后回放"的顺序保证不漏，但基线本身可能持续较长时间。

### 4.6 多实例与故障接管

- 同一任务的 CDC 消费由数据库租约互斥。持锁节点宕机后，其他节点在 `lock-ttl-ms + supervise-interval-ms` 内接管；这段时间内变更延迟会上升。
- 接管后从最后提交的位点重放，重叠窗口由幂等 upsert 吸收，因此仍是 at-least-once。
- H2 元数据库是单写者，多副本部署前必须换成外部 MySQL / PostgreSQL。

### 4.7 延迟指标的口径

状态面板的「延迟」与 Prometheus 的 `jync_task_cdc_lag_seconds` 读的是**最近一个已应用变更在源库产生的时刻**到**本机处理它的时刻**之差，不是「上次事件到现在」的墙钟差 —— 源库空闲是追平，不是落后。各引擎的源时刻来源：

- **MySQL**：binlog 事件头里的时间戳。事务提交只刷新「上次事件」，不会把已测到的延迟覆盖成 0。
- **Oracle LogMiner / 达梦 LogMiner**：`V$LOGMNR_CONTENTS` 的行时间。
- **PostgreSQL 系**：COMMIT 行里的 `(at <时刻>)`。原生 PostgreSQL 由 Jync 打开 `include-timestamp '1'` 取得；openGauss 自带该后缀。服务器不给时间戳时只刷新「上次事件」，延迟维持连接建立时的 0。
- **崖山 YStream**：DML 的 SCN 时间戳；COMMIT / DDL / 元数据 LCR 没有源时间，只算活动。
- **SQL Server**：变更表不携带提交时间，当前版本不测量，延迟显示为 0。要核对真实延迟，请查源库的 `cdc.lsn_time_mapping`，或改用其他引擎的 CDC。

所有引擎在「重启后回放旧事件」时仍会刷新「上次事件」，但不会把重放事件的年龄算成当前延迟 —— 否则空闲源库上的一次重启会把面板钉在最后一条旧事件的时间上，直到源库再次写入。

## 5. 大字段与内存

- 默认开启流式读写：不超过 `inline-max-bytes`（64KB）的值留在堆内，更大的值走流式通道。关闭 `streaming-enabled` 会回到整块读取，堆占用随最大单值放大。
- 主键、游标列与列清洗涉及的列**必须物化**，上限是 `force-inline-max-bytes`（默认 1MB）。超过即报错并指出表、列与配置键——这是有意的硬边界，避免为了"能跑"而悄悄写坏数据。
- PostgreSQL 源库在读取期间保持只读事务（`enable-source-streaming`），代价是读取期间源库的 vacuum 被推迟；大表全量应安排在低峰。
- Oracle CLOB 目标把空串绑定为空 CLOB、VARCHAR2/CHAR 目标仍绑定 NULL；依赖"空串等于 NULL"语义的应用需要自行确认。

## 6. 结构同步与存储过程转换

- 自动建表覆盖表、索引、视图、存储过程/函数，但**不覆盖**触发器、序列的运行时行为、权限、分区策略与表空间等物理属性。目标库的物理设计仍需 DBA 决定。
- 类型映射是保守的：无法确定等价类型时会选择更宽的安全类型，可能带来存储或索引长度差异。
- 存储过程与视图正文的机械转换只处理可判定的语法替换：标识符引号、字符串拼接、可映射的函数、`DECODE` / `NVL2` → `CASE`、标准分页尾部、`CONVERT` → `CAST`、布尔常量、`WITH ROLLUP` 等。过程化控制流、游标语义、异常块、动态 SQL 通常无法可靠翻译——这正是 AI 起草存在的原因，但 AI 只产出**候选**，必须人工审阅后才能落库。
- 无法保证等价的正文构造会**明确阻断并提示 DDL 覆盖**，而不是生成目标库可能执行、但语义或结果错误的 SQL。包括跨方言族的过程化例程正文（`BEGIN/DECLARE`、变量、游标、循环、条件/异常处理）、PostgreSQL `::` 强转、带样式的 SQL Server `CONVERT`、字符集 `CONVERT … USING`、目标方言没有的 JSON 访问符、`IS TRUE/FALSE` 到 SQL Server、Oracle 旧式外连接、`EXCEPT ALL`、MySQL 反斜杠转义字面量等；阻断信息会保留原文供人工改写。同一方言族（如 Oracle → 达梦、PostgreSQL → KingbaseES）不做这道过程化阻断。
- 自增列与列默认值按目标库规则替换：MySQL / PostgreSQL 不接受 DECIMAL/NUMERIC identity（MySQL 8.4、PostgreSQL 16 已实测报错），按精度提升到整数段或 SERIAL；纯 `DATE` 的当前时间默认值改为当前日期表达式；MySQL 零日期在其他产品的时间列上丢弃；SQL Server 高精度时间列改用 `SYSDATETIME()` 系列。HANA 的 DECIMAL identity 按官方文档保留 scale 0、提升正数 scale，**该规则未在 v1.12.0 用真 HANA 重跑**，见[真实数据库验证矩阵](verification-matrix.md)。
- 视图与过程在目标库创建失败时，失败原因会写进日志与页面；修复需要用 DDL 覆盖，而不是反复重跑。

## 7. 调度与多实例

- Quartz 使用**内存存储**。节点重启后按数据库里的启用标志重建调度；停机期间错过的 Cron 触发不会逐个补跑（错过的间隔轮询直接丢弃，Cron 最多补跑一次）。
- 多实例靠数据库租约互斥，但**没有分布式 Quartz 集群**：每个节点都持有调度，实际执行由租约裁决。节点间时钟漂移会影响 Cron 的触发时刻，部署时应统一 NTP。
- Cron 按服务器时区求值。容器或主机时区未固定时，"每天 02:30"可能落在错误的本地时刻。

## 8. 安全边界

- 外部认证的地址由管理员填写，属于 SSRF 面：只填可信内网地址；Jync 只接受 http(s)、不跟随重定向、限制响应体大小。
- 网关头模式只信任 `app.security.trusted-proxies`（默认仅回环）内的直接对端。Jync 必须部署在网关之后，且网关必须剥离客户端伪造的身份头。
- 连接密码用 `data/<库名>.key` 加密。**密钥与元数据库必须成对备份**；密钥丢失后已保存的密码与 AI 密钥无法恢复。
- 默认账号 `admin / 123456`、`view / 123456` 必须在首次登录后改密；未改密前除改密页外全部不可用。

## 9. 规模建议

| 维度 | 建议 |
|---|---|
| 表数量 | 单任务几十到几百张表；上千张表建议拆成多个任务，便于隔离失败与调度 |
| 单表行数 | 百万到千万级是全量与增量都舒适的区间；亿级表建议先评估全量窗口与索引重建时间 |
| 全量并行 | 生产共享库 1，专用迁移窗口 2–4；再高主要是在加压源库与目标库 |
| 增量频率 | 2 秒到 5 分钟；更低延迟用日志 CDC，更高延迟用 Cron |
| 部署实例 | 默认 1 个；需要高可用时换外部元数据库后再增加副本 |

这些不是硬性上限，而是"默认配置下不需要额外调优"的范围。超出时先按 README 的调优步骤测一轮，再决定是否换架构。

## 10. 性能监控

两个性能页面——数据库性能（连接列表的曲线图标）与任务性能（任务列表 / 任务详情页的曲线图标）——都是**旁路观测**，不改任何同步、CDC 或 ETL 的行为；关掉采集只损失这两页。

- **采样由后台定时执行。** 进程资源 60 秒、任务吞吐 60 秒、连接健康与库内指标 300 秒、表数 / 行数 / 占用空间 3600 秒，均可在 `metrics.*` 下调整；`metrics.enabled=false` 全关，已采到的数据仍可查看直到过期。数据库采样覆盖连接列表里的**每一条连接**，包括暂时没有项目引用（或只被停用项目引用）的连接——它们同样有性能页，不能永远显示「暂无采样」。代价是每条连接每 5 分钟开一次即用即还的探测会话，与告警模块对全部连接的定期健康检查同一量级；连接很多时把 `metrics.db-interval-ms` 和 `metrics.capacity-interval-ms` 调大即可。重启后第一次采样在约 30 秒时进行（`metrics.db-initial-delay-ms`），性能页不会空等一个完整间隔。
- **历史保留 7 天**（`metrics.retention-days`），过期样本由后台任务清理。删除连接会连同它的数据库样本一起删除，删除项目会连同它的任务样本一起删除，**不可恢复**。
- **数据库性能页仅管理员可见。** 库内指标描述的是那台服务器上所有会话，不只是 Jync 自己的。任务性能页两种角色都能打开；进程资源（CPU / 堆 / 线程 / GC）属于整台服务器而不是某一个任务，已从任务页移到看板的进程区块，同样仅管理员可见——而且访客拿到的 JSON 里就没有这几项，不是靠页面隐藏。
- **连接的探测会话每次都会归还。** 采样复用连接表单里的账号，另开一个单连接池读完即关，不与同步引擎共享连接池。
- **账号权限。** 读库内运行指标需要对应的字典权限：Oracle 族（含达梦、崖山）需要 `SELECT_CATALOG_ROLE`，SQL Server 需要 `VIEW SERVER STATE`，DB2 需要 `MONITOR`，HANA 需要 `CATALOG READ`；MySQL 与 PostgreSQL 用普通账号即可。缺权限时**只丢掉那一项**，其余指标照常显示；四项都读不到时页面显示占位说明，四张卡保持"—"，不会画成 0。
- **未在真实服务端验证的产品。** Oracle 26ai、YashanDB 23.4、MySQL 8、PostgreSQL 16 已用真库验证；SQL Server、DB2、HANA 本机没有实例，读取器的 SQL 只经过单元测试。首次接入这些产品时请先打开一次性能页确认指标是否读得出来。
- **没有库内指标的产品。** H2、MongoDB 原生驱动、未声明方言家族的自定义连接，以及任何尚未实现读取器的产品，仍然会采到连通性与延迟，但运行指标区块显示占位。容量（表数 / 行数 / 占用空间）只有 MySQL、Oracle、SQL Server、PostgreSQL、DB2 的目录统计能回答；其余产品没有这项查询，三张容量卡保持「—」，不会画成 0。
- **空档不是 0。** 某个时间桶没有采样时，曲线在该处断开；"当前值"取最近一条样本，即使那条样本本身读不到（例如中断期间）也显示"—"，不沿用上一次的旧数字。
- **连接挂掉不影响打开页面。** 页面照常打开，顶部红条说明最后一次探测失败的原因，曲线停在最后一个成功点。
- **Prometheus 指标端点默认关闭。** `GET /api/metrics/prometheus` 按 Prometheus 文本格式输出最新一条进程、任务与连接样本（`jync_up`、`jync_app_*`、`jync_task_*`、`jync_connection_*`）。它不在登录会话之内——采集器无法持有 Jync 会话——因此**只有** `metrics.prometheus-token`（环境变量 `JYN_METRICS_TOKEN`）这一道门：token 为空时端点直接返回 404，配置后必须带 `Authorization: Bearer <token>`，否则 401。stock 安装不暴露项目名与连接名。建议用 HTTPS 或内网访问，并把 token 当作密码管理；轮换方式就是改环境变量后重启。
- **端点是现状快照，不是历史。** 每次抓取只读样本表里每个项目 / 每条连接的最新一行，重采样间隔沿用 `metrics.*`（进程与任务 60 秒、连接 300 秒），两次采样之间数值不变。历史交给 Prometheus 自己保存；Jync 的 7 天曲线仍只服务于页面。
- **读不到的值是 `NaN`，不是 0。** 某项指标该产品不提供（例如 H2 没有库内指标）或本次采样失败时输出 `NaN`；`jync_connection_healthy` 固定为 0/1。告警规则请用 `jync_connection_healthy == 0` 而不是 `latency > 0`，`NaN` 会在比较中落空，正好避免把「没采到」误报成「正常」或「故障」。
- **抓取不触碰源库。** 端点只读已存样本，不会在抓取时打开数据库连接；因此把 scrape 间隔调到 15 秒也不会给生产库增加会话。样本由后台采样任务照常生成，`metrics.enabled=false` 时端点只剩 `jync_up 1`。

## 11. 专属迁移（ES/OpenSearch → Easysearch、MongoDB → MongoDB、MongoDB → KingbaseES）

专属迁移是**手动或 cron 触发的一次性整对象复制**，不是实时同步，也不走 JDBC 能力矩阵。三种类型共用同一套连接、任务、预检、运行历史与取消机制，差异只在对象类型与写入方式。

### 11.1 三种类型共同的限制

- **只复制运行那一刻的数据。** 运行结束后源端的新增、修改、删除不会被回放。需要目标与源一致时，用 `OVERWRITE` 重跑；`APPEND` 只会追加或 upsert，不会删除源端已删除的对象。
- **`OVERWRITE` 会先删除目标同名对象。** 这是破坏性操作：表单默认值与预检都会提示，首次对生产目标运行前务必先跑预检并确认目标名。
- **没有断点续传。** 迁移按对象整体处理：失败后用 `OVERWRITE` 重跑收敛，或用 `APPEND` 幂等追加。中途取消只保留已提交的批次，不会从断点接着跑。
- **取消只在批间生效。** 每批写入完成后才检查取消标志；正在提交的那一批会写完，因此取消后目标上会留下前几个批次的数据。
- **目标命名按各产品的规则校验，不会静默截断。** Easysearch 索引名超过 255 个字符、MongoDB 集合名超过 120 字节（UTF-8）、KingbaseES 标识符超过 63 字节，或名称含非法字符时，预检报 ERROR、运行时该对象计 FAILED，不会截短后冒险创建。
- **行数校验要求源端静止。** `verifyCount` 比较源与目标计数；运行期间源端持续写入会让计数不等，从而把该对象判为失败。大对象请安排低峰期，或关闭计数校验。
- **对象数量与批量大小有上限。** 一次最多 `maxCollections` / `maxIndices`（默认 200）个对象，单批受 `batchSize` 与字节上限约束；超大对象要调小批量并放宽连接超时。
- **运行锁是进程内的。** 同一任务在单实例内不会重叠运行；多实例部署没有分布式租约，两个实例可能同时跑同一个任务。需要多实例时请自行保证同一任务只在一个实例上调度。
- **不迁移分片、用户与角色。** 分片集合的 shard key、zone 与 chunk 分布不复制：`OVERWRITE` 重建出来的集合在目标上是未分片的，需要分片时请在目标端自行 `shardCollection`；`APPEND` 写入目标已有集合时沿用其既有分片设置。GridFS 不做特殊处理，`fs.files` 与 `fs.chunks` 按普通集合复制——两者都迁移且源端静止时目标上可正常读取，但运行期间的写入不保证与源端一致。用户、角色、认证方式与授权不迁移；搜索侧同样不复制安全配置与集群级 settings。

### 11.2 ES/OpenSearch → Easysearch
- **`OVERWRITE` 会先删除目标同名索引。** 这是破坏性操作：表单默认值与预检都会提示，首次对生产目标运行前务必先跑预检并确认索引名。
- **`_source.enabled=false` 的索引无法迁移。** 没有 `_source` 就没有可写入目标文档；预检直接报 ERROR，不进入运行。
- **部分 mapping 类型在 Easysearch 上语义不同或不受支持。** `knn_vector` / `dense_vector`、`sparse_vector`、`rank_features`、`rank_feature`、`flat_object`、`completion`、`search_as_you_type`、`percolator`、`join` 与 runtime fields 预检会 WARN；是否可用取决于目标产品的版本与插件，不要把它当成“一定能迁”。
- **别名默认不复制。** 避免悄悄改变目标集群上已有别名的写入指向；需要时在任务参数里显式打开，冲突只记 WARN，不会让整次运行失败。
- **行数校验要求源端静止。** `verifyCount` 比较源与目标的 `_count`；运行期间源端持续写入会让计数不等，从而把该索引判为失败。大索引请安排低峰期，或关闭计数校验。
- **不复制目标端已有数据之外的历史。** 迁移按索引整体处理，没有索引级断点续传：失败后用 `OVERWRITE` 重跑收敛，或用 `APPEND` 幂等追加。
- **索引数量与批量大小有上限。** 一次最多 `maxIndices`（默认 200）个索引，单个 bulk 请求受 `batchSize` 与 `maxBulkBytes` 约束；超大索引要调小批量并放宽连接超时，否则容易在目标端触发请求体或超时限制。
- **运行锁是进程内的。** 与 ETL 一样，同一任务在单实例内不会重叠运行；多实例部署没有分布式租约，两个实例可能同时跑同一个任务。需要多实例时请自行保证同一任务只在一个实例上调度。
- **Easysearch 兼容性基于 ES 7.x REST。** 实现使用 `_cat`、`_settings`、`_mapping`、`_alias`、`_search?scroll`、`_bulk`、`_count`、`_mget`、`_refresh`；CI 只对假服务与 Elasticsearch 兼容路径做过验证。上线前请用目标 Easysearch 版本试跑一次，重点看 settings 清理、mapping 类型与 `_bulk` 响应。
- **搜索连接独立于数据库连接。** 账号、密码与 API Key 加密存储，页面不回显；关闭 TLS 校验会在审计日志留痕，且只应用于你自己控制的、使用自签名证书的目标。

### 11.3 MongoDB → MongoDB

- **`APPEND` 的语义与 ES 不同。** ES 的 `APPEND` 是按 `_id` upsert，会覆盖目标同 `_id` 文档；MongoDB → MongoDB 的 `APPEND` 保留目标已有文档、`_id` 冲突的文档**跳过**并计 duplicates 且在结果里 WARN，**不覆盖**。需要以源为准时用 `OVERWRITE`；需要幂等覆盖请改用 MongoDB → KingbaseES 的 `upsertOnId`，或先手工清理目标。
- **只复制普通集合。** `view` 与 `timeseries` 集合预检 WARN、运行时 SKIPPED；`system.*` 集合默认排除，除非模式显式以 `system.` 开头。空集合在运行时 SKIPPED，不会删除或重建目标集合。
- **重复键在 `ordered=false` 下是部分成功。** 普通集合用无序插入，一批里部分文档失败不会中断其余文档；写入数以驱动回报的 `insertedCount` 为准。capped 集合必须有序插入，因为插入顺序与淘汰行为有语义。
- **集合选项与索引尽力复制。** 只保留可写选项（`capped`、`size`、`max`、`validator`、`collation` 等），`uuid` 等只读字段被过滤；索引跳过 `_id_` 并去掉 `v` / `ns` / `background`。单个索引创建失败只 WARN，但该集合最终计 FAILED。
- **批量上限按 JSON 字节估算。** 分批同时受条数（默认 1000）与 UTF-8 JSON 字节（默认 8MB）约束；Binary 字段会被 base64 放大，因此实际写入的 BSON 可能与估算不同。远低于服务端 48MB 命令上限仍可能遇到超时，超大文档请调小批量。
- **同一个 MongoDB 集群跨库复制要建两条连接记录。** 任务要求源连接与目标连接不是同一条；同一 host、不同 `databaseName` 的两条记录即可。
- **源与目标指向同一个数据库时任务拒绝运行。** 运行前会解析两条连接（含 URI 路径与 `databaseName`）的实际库名与 host 列表，两者相同时直接判失败（`error.migration.mongo.sameDatabase`），不打开网关。原因是 `OVERWRITE` 会先删目标集合——同库复制会在读源之前就把它删掉。同一 host、不同库名仍允许；用两条连接记录绕不过这条检查。
- **写关注错误不再被当成重复键吞掉。** 只有真正的重复键（11000 / 11001）才计入 duplicates 并按上述规则跳过或失败；`wtimeout` 等写关注错误会原样抛出让该集合计 FAILED，不会被静默当作「已存在」。
- **MongoDB 连接安全。** 密码只存加密字段、页面不回显；**URI 中禁止写密码**，服务端会拒绝。TLS 校验开关对 MongoDB 不生效（表单隐藏），需要时通过 URI 参数（如 `tls=true`、`tlsCAFile`）配置。测试连接与运行日志不输出 URI。

### 11.4 MongoDB → KingbaseES

- **表结构由采样推断，不随数据演进。** 只采样 `sampleLimit`（默认 200）条文档的顶层字段；后续文档出现未采样字段会被忽略，类型冲突会写入失败。需要新字段时改大采样重跑 `OVERWRITE`。
- **嵌套文档与数组写成 TEXT 的 JSON，不展开为列。** `nestedMode` 目前只接受 `JSON`：Document、Array、Null 与混合类型都渲染成 relaxed Extended JSON 文本。想在 KingbaseES 里拆成关系列需要自行建视图或改 SQL。
- **`_id` 是主键。** `createPrimaryKey` 默认开启，`_id` 为 NOT NULL 且有主键约束；抽样中没有 `_id` 的集合直接失败（无键可建），不会退化成无主键表。关掉主键时 `_id` 可空，但同一批里重复 `_id` 不会被约束拦截。
- **`upsertOnId` 需要主键。** 打开后生成 `INSERT … ON CONFLICT ("_id") DO UPDATE`，因此必须同时开启 `createPrimaryKey`；否则选项校验报错。它为 `APPEND` 提供了幂等重跑，但不会删除源端已删除的行。
- **字段名必须能直接作为普通标识符。** 采样推断出的顶层字段名要匹配 `[\p{L}_][\p{L}\p{N}_$#]*`（字母或下划线开头，后接字母、数字、`_`、`$`、`#`）；含点号、空格、连字符等字符的字段名预检报 ERROR，不会引用后冒险建表。
- **`APPEND` 到已有表要求列对得上，且按列名精确大小写匹配。** 写入器按推断出的原始字段名绑定列，大小写折叠的「近似匹配」会让预检通过、首批写入才失败，因此这里不做忽略大小写比较。目标缺列、或目标多出 NOT NULL 且无默认值的列，预检报 ERROR；类型不匹配只 WARN，由数据库在写入时决定是否接受。
- **`APPEND` + `upsertOnId` 要求目标表 `_id` 已有唯一索引或主键。** 否则 `ON CONFLICT ("_id")` 在 KingbaseES 上无法定位冲突，会在运行时报错；预检会检查唯一约束，缺失时报 ERROR（`migration.precheck.table.idNotUnique`）。
- **建表类型受共享 PostgreSQL 方言约束。** ObjectId → VARCHAR(24)，String → TEXT，整数 / 长整数 / 浮点 / 小数 / 布尔 / 日期按 BSON 类型映射，Binary → BYTEA。PostgreSQL 的 `BYTEA` 参数必须用 `setBytes` 绑定（驱动已处理），不要把二进制列改写成 `oid`。
- **KingbaseES 连接安全。** 仅支持 BASIC 认证，账号与密码只存加密字段；**JDBC URL 与 extraParams 中禁止出现 `user` / `password`**，服务端会拒绝。`schemaName` 留空使用连接的当前 schema；schema 与表名按 63 字节校验，所有 DDL/DML 都经方言引用标识符。目标 schema 不存在时预检报 ERROR（`migration.precheck.schema.missing`），不会隐式建 schema。
- **没有跨集合事务。** 每个集合的 DDL 立即提交、数据按批提交；某一集合失败不会回滚其他集合，`continueOnError` 打开时继续处理下一个集合，最终整体计 FAILED。
- **真库验证范围。** CI 用 PostgreSQL 16 容器验证共享方言（建表、类型、INSERT、`ON CONFLICT`、回滚），真实 KingbaseES 走可选的环境变量集成测试（`JYNC_KINGBASE_IT_URL` 等）。已在 **KingbaseES V9R1C1B25** 的 PostgreSQL 与 Oracle 两种兼容模式下跑通建表、带 SQL NULL 的批量插入、计数、`ON CONFLICT` upsert、`_id` 存在性检查与删表。**更老的 V8R3 不兼容随包内置的 9.x 驱动**：该版本的目录只有 `SYS_CATALOG`、没有 `PG_CATALOG` 兼容视图，驱动的元数据查询会报 `PG_CATALOG.PG_namespace` 不存在；请升级到 V9（或厂商支持的更新版本）。上线前仍建议用目标版本试跑一次，重点看类型映射、schema 与标识符大写规则。
