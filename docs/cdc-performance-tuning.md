# CDC 性能调优与真实库压测操作手册

本文只处理日志 CDC（MySQL binlog、PostgreSQL logical、Oracle/DM LogMiner、SQL Server CDC、Yashan YStream）的**消费滞后**。轮询同步和全量加载的参数不同，见 `docs/configuration.md`。

## 先判断是“慢”还是“已经丢了”

### 1. 位点已 PURGED

页面或日志出现：

```text
PURGED: Could not find first log file name in binary log index file
ORA-01291 / missing redo
```

含义是持久化位点所在的源日志文件已经被清理。此时：

- 重连、调 batch、重启消费者都不能恢复；
- 先在源库/RDS 调大日志保留期，并确认磁盘空间；
- 再停止任务，执行「重建基线」；
- 基线完成后从新位点开始消费。

如果位点更新时间和源库保留期相比已经很旧，说明消费者不是“暂时慢”，而是已经停过一段时间。先查消费者在哪个节点持锁、节点是否存活、任务是否被错误状态停住。

### 2. 位点仍在推进，只是落后

看 CDC 状态卡：

- **位点年龄**：持久化位点已经多少秒没有推进；
- **事件延迟**：最新一条事件在应用时已经落后源库多少秒；
- **目标批量耗时**：最近 / 平均 / 峰值，以及每秒写入行数；
- **上次事件**：消费者最后一次处理事件的绝对时间。

如果事件延迟持续增长、目标批量耗时也增长，瓶颈通常在目标写入或目标网络；如果延迟增长但批量耗时正常，检查源端事件量、消费者是否频繁重连，以及目标提交之外的时间。

## 手动调参顺序

### 1. 先确认源库保留期

MySQL/RDS 示例：

```sql
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
SHOW VARIABLES LIKE 'expire_logs_days';
SHOW MASTER STATUS;
SHOW BINARY LOGS;
```

保留期至少要覆盖：

```text
预期最长停机时间 + 一次全量基线耗时 + 安全余量
```

大表基线可能需要数小时；如果保留期只有几分钟，基线刚做完日志又会被清掉。

### 2. 调 `sync.batch-size`

这是增量轮询和 CDC 回放共用的**目标端 JDBC 批量**，默认 500，范围 1–20000。

- 系统管理 → 系统配置，或让 AI 助手调用 `update_system_params` 设置 `sync.batch-size`；
- **本节点保存后，运行中的 CDC 消费者下一批立即读取新值**；
- 其他节点约 30 秒刷新后生效；轮询任务下一轮生效；
- 项目级 `batchSize` 只影响全量加载，不影响 CDC。

建议从 500 → 1000 → 2000 小步调整，每次观察：

- 目标批量耗时是否下降；
- 目标 CPU、IO、redo/undo、锁等待是否上升；
- 事件延迟是否持续下降；
- 是否出现新的写入超时或死锁。

不要一次调到 20000。批量越大，目标单笔事务越大，失败重放和锁持有时间也越长。目标已经接近 IO/CPU 上限时，调大 batch 可能更慢。

### 3. 目标端检查

- 目标表二级索引是否过多；CDC 回放期间是否需要暂时减少非必要索引；
- 是否有触发器、审计、级联操作；
- Oracle 重点看 redo/archive 空间、IO 延迟和提交等待；
- 目标连接池是否被其他任务占满；
- 网络 RTT 是否很高；高延迟链路通常更值得增大 batch。

### 4. 源端检查

- 峰值事务数、单事务行数/字节数；
- 是否存在大量超大事务；超大事务会按 `sync.cdc.max-transaction-rows` / `max-transaction-bytes` 停车；
- binlog 压缩、网络带宽、代理空闲超时；
- 不要在同一源库上运行多个 Jync 消费者；确认当前消费者在哪个节点持锁。

### 5. 仍追不上时

Jync 当前是**每个 CDC 项目单消费者线程**，一个源事务对应一次目标提交。目标提交延迟高、源端事务很碎时，单线程可能达到上限。可以考虑：

- 拆分项目/按业务表拆成多个任务；
- 把目标库 IO、索引维护、触发器移出回放高峰；
- 对极大历史积压先重建基线，而不是指望 CDC 追上已清理的日志；
- 把性能数据保存下来再评估是否需要并行 apply 或事务级合并，不能直接在生产猜测。

## 真实库压测建议

至少覆盖目标产品实际使用的组合。每组记录：

- 源库/目标库版本、网络 RTT、目标 IO；
- 数据量、表宽度、索引数、LOB 比例；
- 事件速率（rows/s、transactions/s）；
- batch 500 / 1000 / 2000 的批量耗时、峰值、错误数；
- 事件延迟和位点年龄曲线；
- 目标 CPU、IO、锁等待、redo 增长。

推荐矩阵：

| 场景 | 关注点 |
|---|---|
| MySQL → Oracle | Oracle 提交/redo、索引维护、LOB |
| MySQL → MySQL | 目标唯一索引、死锁、batch 大小 |
| PostgreSQL logical → 目标库 | slot 滞留 WAL、目标写入延迟 |
| SQL Server CDC → 目标库 | 窗口大小、单事务内存、目标提交 |
| 含 LOB 的 MySQL → Oracle | spill、批量重绑定、事件延迟 |
| 200+ 表项目 | 表切换、连接池争用、状态轮询开销 |

压测时先让源端产生稳定事件流（sysbench 或业务回放），至少跑过一轮目标 checkpoint/redo 周期；不要用 10 秒的峰值判断长期吞吐。

## AI 助手调节

管理员可以直接对助手说：

```text
把 MySQL→Oracle 任务的 CDC batch 调到 2000，观察下一轮批量耗时
```

助手会调用 `update_system_params` 生成确认卡。确认后：

- 本节点正在运行的 CDC 消费者下一批即使用新值；
- 其他节点约 30 秒收敛；
- 轮询任务下一轮使用新值。

助手不会自动反复调参；每次只建议一项改动，并要求观察批量耗时、事件延迟和目标错误后再决定下一步。

## PURGED 处置清单

1. 停止任务，确认没有消费者持锁；
2. 修好源/目标连接；
3. 调大日志保留期并确认空间；
4. 重建基线；
5. 启动后确认位点年龄和事件延迟下降；
6. 如仍落后，按上面的顺序调 `sync.batch-size` 和目标端。
